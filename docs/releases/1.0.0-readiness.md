## Scope and limits

- Supported release boundary: standalone, one worker, one replica, canonical Compose,
  SQLite Core. No schema migration or operator-data reset is required by these repairs.
- The 22 skips are existing live PostgreSQL/MongoDB migration, identity and usage-ledger
  tests without configured test databases. External OIDC and real vendor OAuth,
  billing, quota renewal and paid inference were not certified.
- Chromium and deterministic provider fixtures do not certify Firefox/WebKit, all
  assistive technologies, ARM64, or every real account/content combination.
- The optional ten-minute soak was not rerun. Runtime fixture ResourceWarnings are
  retained in logs; they were not suppressed to obtain a passing result.
- Registry checks are read-only. Credential names being present in CI does not prove
  registry write credentials remain valid; publication itself is not rehearsed here.

## Authorized publication sequence

1. Obtain approval to merge and publish. Check green required CI on the approved final
   SHA, an unchanged source tree, the publication date and current tag/image availability.
2. Merge only the reviewed candidate. If integration changes the tested source, rerun
   required checks; tag and build from the same approved immutable revision.
3. Publish `v1.0.0` / image `1.0.0` using the guarded workflow. Verify source revision,
   registry digests, release notes and GitHub's latest stable release selection.
4. Rehearse installation from the actual published digest and verify About/update
   metadata. Back up each real deployment before upgrading; never reset its storage.
5. Monitor health, error rates and latency after deployment. Use the previous verified
   digest and encrypted backup for recovery following [updating](../updating.md).

The [preparation checklist](1.0.0-preparation.md) records pending publication actions;
the [audit](../audits/release-readiness-2026-09-18.md) preserves findings and earlier
failed runs without relabeling them as successes.
