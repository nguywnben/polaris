# W4.15 Redis Semantic Primitive Parity Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement versioned, fenced, bounded coordination semantics with in-process and Redis
parity without activating coordinated mode.

**Architecture:** A strict domain module defines fencing epoch, CAS, invalidation, and compatibility
quota contracts. The in-process implementation is the executable reference; Redis uses fixed
bounded Lua scripts and a strict reply codec behind the same Python interface. Existing runtime
callers remain on the in-process path until W4.16–W4.18.

**Tech Stack:** Python 3.12/3.14, redis-py 8.1.x asyncio client, Redis 8 Lua 5.1 scripting,
`unittest.IsolatedAsyncioTestCase`, existing Prometheus text renderer.

**Spec:** `docs/specs/coordination-store.md`

## Global constraints

- Keep `WORKERS=1`, one application replica, source authority, and every HA activation gate.
- Do not move session, OIDC, routing, credential, cache, or runtime quota callers in W4.15.
- All production behavior follows RED→GREEN→REFACTOR; every test must be observed failing first.
- Every mutation is schema-versioned, bounded, namespaced, idempotent, and fenced by the exact
  ready epoch.
- Redis keys and telemetry contain no plaintext secret, bearer token, identity, or caller payload.
- No best-effort distributed lock is a correctness primitive.
- Live Redis is opt-in through `POLARIS_TEST_REDIS_URI`; absence is reported as a skip, not a pass.
- No external source transfer or cross-model CLI invocation occurs without artifact-specific human
  authorization.
