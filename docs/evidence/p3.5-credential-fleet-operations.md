# P3.5 — Credential Fleet Operations

Date: 2026-09-10
Plan: `PROD-SELFHOST-R1`
Status: complete

## Result

The Credentials page now presents the common fleet workflow first: select the current page, run
only actions supported by every selected credential type, narrow the fleet with four primary
filters, and disclose six diagnostic filters only when needed. The operator can see the number of
active filters and reset the complete query with one action. English and Vietnamese copy is
curated; other supported locales receive the English fallback already used by the console.

Page, page size, and validated filters survive refresh and reload through bounded URL/session
state. Page-scoped selections retain only credentials still visible after refresh, and a page that
no longer exists is clamped to the last valid page. The select-page checkbox now follows the same
identifier contract as the manager, and credential cards no longer reference removed provider
flags when real data is rendered.

Mixed-provider actions are calculated as an intersection of the authenticated capability catalog.
Provider-specific actions disappear when any selected variant does not support them. Both explicit
page selections and all-matching selections are limited to 100 targets in the console and again at
the API boundary. All-matching mutations show the human-readable filters, server query
fingerprint, eligible/skipped/total impact, and the action confirmation before execution. Existing
preview tokens, idempotency keys, per-item typed results, stale-preview rejection, quota/reset,
cooldown, model count, and per-credential diagnostics remain intact.

## Scope Boundary

P3.5 changes the credential-fleet presentation and client orchestration around existing versioned
status, capability, preview, and batch APIs. It does not add a fleet service, database table,
dependency, polling loop, provider, background job, distributed coordinator, or experimental HA
requirement. No live credential was created, changed, exported, or deleted during browser testing.

Models and routing remain the next fixed task, P3.6. The seven static English pagination literals
introduced in the committed P3.4 Providers fragment are not a P3.5 regression; they remain visible
as a pre-existing localization finding owned by the fixed P4.6 localization closure rather than
expanding this task.

## Post-implementation Review

The correctness, readability, architecture, security, performance, and simplification review found
and corrected four issues before completion:

1. the page checkbox used an identifier different from the manager contract, so select-page state
   could not be synchronized;
2. explicit 101–200 item selections bypassed the client bound even though the API rejected them;
3. card rendering still referenced two provider flags removed in an earlier change and could fail
   as soon as a credential was present; and
4. the active-filter summary initially updated only after reload instead of during the filter
   interaction.

Filter values are allowlisted before persistence, session payloads remain bounded, and the query
fingerprint is server-generated. External credential labels and diagnostics continue through the
existing safe text/escaping paths; no secret is added to URLs, browser storage, previews, logs, or
test fixtures. List reads remain paginated, batch work remains bounded, and the change adds no
network request beyond existing refreshes. No dead compatibility branch or new dependency remains.
The three unrelated user-owned working-tree changes were not staged or modified.

P3.5 completes progress **23/36** and Phase 3 progress **5/6**. The next fixed task is P3.6 — Models
and routing workflow.
