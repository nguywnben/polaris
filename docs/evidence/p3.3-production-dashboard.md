# P3.3 — Production Dashboard

Date: 2026-09-10
Plan: `PROD-SELFHOST-R1`
Status: complete

## Result

The Dashboard now starts with one readiness decision and one next action instead of treating
service-objective terminology as the primary product experience. First-time, no-active-provider,
healthy/ready, and degraded states direct the operator to Provider onboarding, Credentials, or
Activity as appropriate. Current 15-minute health takes precedence over historical period errors,
so a healthy gateway is not left in a false degraded state by older failures.

The primary information order is readiness, quick actions, request/credential/cost/latency
indicators, provider and credential incidents, request health, recent activity, and usage trends.
Low-value requests-per-credential and tokens-per-request cards were removed. Prometheus and
OpenTelemetry status remains available under a collapsed advanced-monitoring disclosure instead
of occupying a primary card.

Recent Activity displays at most five content-free request traces. Usage details request at most
100 rows, sorted by request volume, and the API response reports `page_size`, `total_items`, and
`has_more`. Request health renders at most ten route rows. Dashboard startup has a fixed four-call
budget: bounded usage details, aggregate totals, current operational health, and five recent
traces.

## Scope Boundary

This task changes Dashboard prioritization and its bounded read model only. It does not add a
frontend framework, dependency, database schema, polling loop, background job, commercial tenant
concept, SLO enforcement system, or experimental HA activation. Full provider onboarding,
credential fleet operations, and routing workflow changes remain P3.4–P3.6.

English and Vietnamese Dashboard copy is curated in P3.3. The other supported locales receive the
complete English fallback set so no raw key is rendered; comprehensive locale completion remains
the fixed P4.6 task.

## Post-implementation Review

The five-axis review covered correctness, readability, architecture, security, and performance. It
found and corrected three required issues before approval:

1. period-wide error history could override a currently healthy 15-minute health snapshot and
   produce a false degraded banner. Historical error rate is now used only when current health has
   no signal, with a regression fixture; and
2. the desktop flex header retained a wide min-content size between 601 and 960 px, causing tablet
   overflow. The Dashboard header now collapses at the tablet breakpoint; screenshots and measured
   scroll widths prove the correction; and
3. a zero-filled time series used a forced minimum of one both for chart scaling and the displayed
   peak, contradicting the zero-request total. Scaling and the truthful peak label are now separate,
   and a behavior test covers the empty-traffic case.

All trace-derived text and attributes are encoded before HTML insertion; request content is neither
returned nor rendered. Existing authenticated routes are reused, all list reads are bounded, and
no new dependency or unbounded refresh behavior was introduced. One-use recent-trace state was
removed during simplification. No dead code was identified. The three unrelated user-owned
working-tree changes were not staged or modified.
