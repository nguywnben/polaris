# P1.5 — Compose Update and Rollback

Date: 2026-09-09
Plan: `PROD-SELFHOST-R1`
Candidate: `7323548`
Status: complete

## Result

The canonical standalone SQLite Compose deployment now has one cross-platform host workflow for
read-only planning, pinned image resolution, encrypted pre-update backup, health-checked recreate,
automatic state-and-image rollback, and explicit recovery-record rollback. No dependency, runtime
service, database table, API endpoint, release controller, or HA path was added.

Versioned registry references are pulled once and resolved to a local immutable image ID before
mutation. Untagged references, `latest`, `edge`, malformed records, altered backup checksums,
unrelated active images, external storage, multiple workers/replicas, and missing named volumes
fail closed. Preflight also compares the effective Compose environment and published port with the
running container without printing their values, preventing a missing `.env` from silently changing
authentication or port configuration.

The backup passphrase travels only through a bounded standard-input frame. The encrypted `.ogb`
and checksum-bound JSON record are atomically persisted outside the Docker volume. Record and
archive sizes are checked before content reads. Offline restore runs with UID/GID `10001:10001`
while `app` is stopped, then the previous immutable image must become healthy.

## Review

The final five-axis review found no unresolved correctness, security, architecture, readability, or
performance blocker. The main complexity is confined to one host tool and one internal recovery
entry point; the protocol boundary and runtime adapter remain directly testable. Standard-library
code and the P1.4 backup implementation were reused, and no speculative release platform or
retention subsystem was introduced. The fixed plan does not require another cross-model review for
P1.5.
