# P0.3 Evidence — Experimental HA Isolation

## Result

P0.3 is complete. The default Production Self-Hosted R1 path remains standalone with one worker and
one replica, requires neither Redis nor HA evidence, and cannot enter coordinated mode accidentally.
The unfinished coordination implementation and its tests are preserved as an explicitly named,
independently runnable experimental suite.

## Runtime Boundary

- `initialize_ha_runtime` checks activation before constructing a coordination storage adapter, so a
  rejected coordinated start performs no Redis or external-storage I/O.
- Coordinated startup requires the exact opt-in `POLARIS_EXPERIMENTAL_COORDINATION=true` and an accepted
  compiled activation record.
- The activation allowlist is intentionally empty in this build. Even an explicit opt-in therefore
  fails closed with a clear experimental-status error and makes no production HA claim.
- The existing one-worker and one-replica policy guards remain active.
- The canonical Docker Compose service no longer forwards Redis or coordination identity variables;
  its defaults remain `standalone`, one worker, and one replica.

## Test and Release-Gate Partition

`backend/tests/suite_manifest.py` owns the checked partition:

- 165 core test modules are the default `python -m backend.tests` surface;
- 13 unfinished coordination/evidence modules are isolated under `experimental-ha`;
- the two HA startup-safety modules remain in core;
- an audit fails if a new `test_ha_*` or `*_redis_live` module bypasses the experimental manifest.

The supported commands are:

```text
python -m backend.tests --audit
python -m backend.tests --suite core
python -m backend.tests --suite experimental-ha
python -m backend.tests --suite experimental-ha --list
```

CI and the R1 release checklist require the partition audit and core suite only. External
two-replica evidence and the experimental suite are not normal release or resume gates.

## Verification

### Focused P0.3 gate

```text
Ran 35 tests in 1.001s
OK
```

This gate covers default startup without Redis, rejection before external I/O, the empty activation
allowlist, suite partition integrity, canonical Compose inputs, CI commands, release-checklist
commands, HA policy/lifecycle safety, deployment assets, and the product inventory.

### Independent experimental suite

```text
Ran 141 tests in 61.946s
OK (skipped=32)
```

The 109 executed cases passed. The 32 skips are the existing opt-in live Redis or external-topology
cases, not newly disabled tests. `python -m backend.tests --audit` reported a valid partition of 165
core modules and 13 experimental modules.

Ruff lint and format checks, `python -m compileall -q backend`, strict YAML lint for CI and Compose,
and `git diff --check` passed. The full core suite is intentionally reserved for the Phase 0 exit
gate under the fixed verification cadence; P0.3 did not create another full-suite run.

## Review

- Correctness: the production initialization path is gated before adapter construction, while
  evidence tooling can continue to exercise the preserved implementation directly.
- Security: environment input is treated as untrusted; activation requires an exact opt-in and still
  fails closed against the empty allowlist. No secret is logged.
- Architecture: activation policy is centralized in `ha_activation`, and suite ownership is
  centralized in one manifest instead of scattered skips.
- CI and maintainability: core safety coverage remains mandatory; unfinished topology tests are
  visible, named, audited, and runnable without becoming an R1 release blocker.
- Performance: the default test path no longer pays for the 141-case experimental topology suite or
  waits for external services. Runtime behavior changes only during startup validation.
- Scope: no coordinated-mode production claim, Kubernetes promotion, topology redesign, dependency,
  or P0.4 work was added.

Verdict: approved for the Production Self-Hosted R1 baseline.
