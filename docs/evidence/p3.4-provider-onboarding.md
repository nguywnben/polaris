# P3.4 — Provider Onboarding

Date: 2026-09-10
Plan: `PROD-SELFHOST-R1`
Status: complete

## Result

The Providers page now consumes the authenticated, versioned provider-capability catalog instead
of presenting its badges as an independent source of truth. All nine advertised connection
variants are matched to one selector, one onboarding workspace, their actual credential type, and
the common production lifecycle: add, test, discover models, disable, and delete. A failed catalog
refresh leaves the built-in onboarding choices usable and exposes an explicit retry action.

The first-use path remains visible while batch import and provider-specific settings are native,
keyboard-accessible disclosures. Settings are loaded only when their disclosure is opened, and a
single in-flight request is shared for variants in the same provider family. Opening Providers no
longer eagerly requests the Antigravity, AI Studio, xAI, OpenAI, and Anthropic configuration APIs.

Existing field contracts continue to supply provider-specific type, required/optional state,
length bounds, URL validation, environment locks, contextual help, and transient-secret clearing.
Successful onboarding hands the operator to Credentials, where capability-derived controls own
edit, test, enable/disable, and removal. Provider failures now map bounded diagnostic categories to
actionable credential, permission, quota, rate-limit, model, network, or upstream guidance.

## Scope Boundary

P3.4 changes provider discovery, onboarding presentation, lazy configuration loading, and failure
guidance. It does not duplicate credential lifecycle controls on the Providers page, alter provider
or credential APIs, add a provider family, store form secrets in browser storage, or change fleet
selection and batch behavior. Faceted fleet operations remain the fixed P3.5 task.

No runtime dependency, database migration, polling loop, background job, enterprise control plane,
or experimental HA behavior was added. The canonical provider-workspace map is reused rather than
maintaining a second client-side variant registry.

## Post-implementation Review

The correctness, interface, architecture, security, performance, and simplification review found
and corrected three issues before completion:

1. provider settings were initially still requested for every family on page entry; the route now
   loads only onboarding capability metadata and defers settings to the opened disclosure;
2. the first disclosure selector missed advanced panels nested outside the two-column tool grid;
   the enhancement now searches the complete active workspace; and
3. a duplicate variant-to-workspace mapping could drift from navigation; onboarding now reuses the
   canonical navigation registry and only adds each provider family's lazy-loader key there.

Capability payloads are strictly shape-checked before they influence the interface, unknown
operations fail validation, external diagnostic text is rendered as text rather than HTML, and no
credential material is logged or persisted by the new workflow. Loader coalescing is bounded to an
active request and failed loads remain retryable. No dead code or additional abstraction was kept.
The three unrelated user-owned working-tree changes were not staged or modified.
