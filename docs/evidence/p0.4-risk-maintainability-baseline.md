# P0.4 Evidence — Risk and Maintainability Baseline

## Result

P0.4 is complete. Polaris now has a checked, reproducible static inventory and a bounded risk
register for the Production Self-Hosted R1 plan. The baseline records risk; it does not authorize a
repository-wide refactor, and file size alone does not authorize any extraction.

The machine-readable baseline is `docs/audits/maintainability-baseline.json`. The standard-library
collector is `tools/maintainability_inventory.py`, so reproducing the measurements requires no new
dependency or external service.

## Recorded Baseline

- 9 runtime modules are at least 1,500 lines. They are assigned by owning workflow: protocol and AI
  conversion to P2.3/P2.4, credential console to P3.5, identity sessions to P5.2, storage to P5.1,
  locale catalogs to P4.6, and experimental Redis state to the post-R1 backlog.
- 7 persistence families have parallel backend implementations: audit, durable-family barrier,
  identity, migration checkpoints, request traces, state manager, and usage ledger. SQLite remains
  Core, PostgreSQL Advanced, and MongoDB Compatibility; P5.1 owns the bounded tier/parity work.
- 8 Pydantic v1-style sites remain: one legacy `dict` call and seven class-based configuration
  declarations. Their owning protocol, quality, and storage tasks will modernize them only with
  relevant contract coverage.
- 480 broad exception handlers occur across 96 runtime files; 305 contain no explicit re-raise.
  This is an inspection proxy, not a claim that 305 bugs exist: deliberate boundary fallbacks may
  log, translate, or return safely. P2.2/P2.4/P5.1/P5.2 own task-local review of the high-risk paths.
- 11 conditional skip sites and 7 live/environment-gated test modules are recorded. Experimental
  Redis/HA coverage stays post-R1; optional PostgreSQL/MongoDB storage coverage belongs to P5.1.
- The frontend contains 45 JavaScript modules, no package-owned test runner, no native JavaScript
  test files, and no maintained browser-harness configuration. Four focused backend/Node contract
  modules are identified, but they do not cover the required browser journeys. P3.2 and P5.4 own
  that gap.

The risk register contains 12 bounded entries: 7 high and 5 medium. Every entry names an existing
P0–P5 task or `POST-R1`; no new task, wave, phase, or denominator was created.

## Reproduction Commands

Run from the repository root on Windows:

```text
.venv\Scripts\python.exe tools\maintainability_inventory.py
.venv\Scripts\python.exe tools\maintainability_inventory.py --check docs\audits\maintainability-baseline.json
.venv\Scripts\python.exe -m unittest backend.tests.test_maintainability_baseline -v
```

The first command prints the live JSON inventory. The second exits non-zero when checked
measurements drift from the saved baseline. The contract test also verifies that all requested
categories exist, every risk has a valid fixed-plan owner, and large-module entries do not silently
authorize refactoring.

## Review

- Correctness: counts come from parsed Python syntax and deterministic repository traversal rather
  than copied search-result totals; saved inventory drift fails the contract.
- Readability: raw locations are retained where they are actionable, while broad-handler results
  are aggregated by area and top hotspot to keep the baseline reviewable.
- Architecture: the collector is read-only, standard-library-only tooling and is not imported by
  runtime code. Risk remediation stays with the existing workflow owner.
- Security: the collector reads source structure only, performs no network I/O, and emits no
  configuration values or secret contents.
- Performance: the focused collector completes in seconds and is not added to the runtime path or
  CI in advance of P0.5 gate design.
- Scope: no hotspot, persistence family, Pydantic model, exception path, skip, or frontend module
  was refactored merely because it appeared in this inventory.

Verdict: approved as the fixed P0.4 production-risk baseline.
