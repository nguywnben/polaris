# P5.1 — Storage Tiers and Migrations Evidence

Date: 2026-09-11

Plan: `PROD-SELFHOST-R1`

Result: **PASS**

## Outcome

SQLite is now the explicit Core storage authority for the supported one-worker, one-replica
product. Existing state is checked read-only before startup writes, schema compatibility changes
are atomic, and every application SQLite connection uses one foreign-key and writer-wait policy.
PostgreSQL remains an optional Advanced backend and passed its live contract against PostgreSQL 17.
MongoDB is explicitly frozen at Compatibility and passed the required driver-boundary smoke without
adding parity work or a live R1 dependency.

## Core SQLite closure

- A bounded ten-second read-only `quick_check(1)` runs on an existing `credentials.db` before WAL
  activation, table creation, compatibility migration, or filename repair. Corrupt/unreadable state
  fails with stable restore guidance and the original file is not changed.
- The additive schema upgrade, table/index creation, and legacy filename repair now run inside one
  `BEGIN IMMEDIATE` transaction. An injected failure after all missing columns were added proved the
  transaction rolls back to the exact original three-column fixture.
- `open_sqlite` is the single connection policy used by credential/config, audit, identity,
  migration checkpoint, request trace, usage ledger, and durable-family SQLite paths. It enables
  foreign keys and a five-second busy timeout on each connection while retaining WAL initialization.
- A competing writer test proved a short lock is waited out and the pending write commits after the
  lock is released.
- The immutable pre-R1 fixture still preserves credentials and configuration through the forward
  upgrade. Existing encrypted backup/validate/restore and update rollback tests remain the supported
  recovery path; no destructive down-migration was introduced.

## External tier closure

- Explicit PostgreSQL or MongoDB startup failure still stops startup without SQLite fallback, and
  simultaneous external URIs remain rejected.
- The optional storage-live suite was run against a disposable local `postgres:17-alpine` container
  using an isolated test database. The first run exposed a stale live-test call to the removed
  `append_entry` name; the contract now calls the current `append_usage` repository interface.
- The rerun completed **25 tests: 15 passed and 10 MongoDB-live tests skipped**. This includes all
  **12 PostgreSQL live cases** and three SQLite migration cases. The disposable PostgreSQL container
  was stopped and removed after the run.
- **31 MongoDB compatibility, storage-selection, and capability-tier smoke tests passed** without a
  live MongoDB service. Requiring or expanding live MongoDB parity would contradict the fixed R1
  Compatibility tier.
- No deprecated Pydantic `class Config` or `.dict()` usage was present in the touched storage paths;
  no unrelated model schema was changed.

## Documentation and operator boundary

- `docs/storage.md` is the canonical tier, outage, migration, and recovery contract.
- English and Vietnamese READMEs now distinguish SQLite Core, PostgreSQL Advanced, and MongoDB
  Compatibility instead of presenting external backends as equivalent replacements.
- The storage outage runbook covers corruption, writer locks, external fail-closed behavior, and
  post-recovery persistence checks.
- The retained durable-ledger migration document is labeled experimental historical design. R1 has
  no supported live cross-backend conversion command, and those tests cannot block SQLite
  production.
