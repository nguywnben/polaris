# P0.6 Evidence — Compatibility and Deprecation Guard

## Result

P0.6 and Phase 0 are complete. Polaris now has an immutable, versioned R1 compatibility
fixture plus an executable guard that fails when a protected route or stored contract is removed or
semantically changed. Additive product work remains allowed; breaking a protected contract requires
an explicit replacement, compatibility path, migration, changelog notice, and a newly named fixture.

The operator policy is `docs/compatibility.md`, the executable guard is
`tools/compatibility_snapshot.py`, and the fixed artifact is
`docs/compatibility/r1-compatibility-v1.json`.

## Protected Surface

The `r1-v1` fixture records and checks:

- 18 public inference operations across OpenAI, Anthropic, Gemini, and Vertex paths;
- 112 management operations under `/api/`;
- resolved request/response OpenAPI fingerprints with documentation-only text excluded;
- 18 server-side console paths, 11 canonical tabs, and three existing compatibility aliases;
- ten legacy environment renames, the removed `PASSWORD` startup error, four stored-key migrations,
  and five removed stored keys;
- nine durable record schema versions; and
- seven Python/Node client examples with checked source markers.

The command has only read/check and print-for-review modes. It intentionally has no command that
overwrites the accepted fixture.

## Upgrade and Lifecycle Defects Found

The versioned `pre-r1-sqlite-v1.json` fixture creates a populated unversioned credential store,
loads it through the current SQLite manager, and verifies credential/config preservation, legacy
key migration, filename repair, added columns, and timestamps for both old and new rows.

This exposed a production upgrade defect: SQLite rejects `ALTER TABLE ... ADD COLUMN` with the
non-constant `unixepoch()` default when the table already contains rows. The migration now adds
plain timestamp columns, backfills existing rows, supplies timestamps on new writes, and fails
closed if schema compatibility cannot be established.

The Phase 0 Core run also exposed a lifecycle leak: after the standalone runtime closed, the global
response cache still referenced its closed state store. Runtime close and failed initialization now
restore a fresh process-local coordination boundary. A regression test reproduces the exact
`runtime close -> cache store/read` sequence.

## Review

- Correctness: route fingerprints resolve local schemas; the upgrade fixture uses a populated old
  database; removals and semantic changes fail while additive surfaces pass.
- Readability: compatibility policy, baseline, fixture, tests, and command each have one explicit
  responsibility.
- Architecture: the guard depends only on the standard library and existing application OpenAPI;
  it adds no runtime service or dependency.
- Security: fixtures contain placeholders only, client examples are checked by markers rather than
  executing credentials, and migration failure no longer leaves a partially compatible store in
  service.
- Performance: the guard is part of configuration contracts, not an HA or live-provider matrix;
  normal task work remains focused.
- Scope: P1 typed configuration, UI consolidation, browser automation, backup/restore, and final
  release work remain in their fixed existing tasks. No task, Wave, phase, or denominator was added.

Verdict: approved. Phase 0 is closed at 6/6; the next fixed task is P1.1.
