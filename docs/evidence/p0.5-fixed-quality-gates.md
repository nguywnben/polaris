# P0.5 Evidence — Fixed Quality Gates

## Result

P0.5 is complete. Polaris now exposes one cross-platform gate runner with explicit `fast`,
`task`, `phase`, and `release` scopes. Contributors can verify an edit without running the complete
Core suite or any HA matrix, while the release plan still names every required production check.

The executable contract is `tools/quality_gate.py`; the operator/contributor reference is
`docs/quality-gates.md`.

## Gate Contract

- `fast` runs backend/tooling lint and format, Python compilation, test-partition audit, recursive
  syntax checks for 45 JavaScript files and 6 deployment shell scripts, strict YAML lint, and both
  working-tree/staged whitespace checks.
- `task` runs `fast` plus one or more explicitly named Core test modules. An empty selection or a
  module assigned to experimental HA is rejected before commands run.
- `phase` runs `fast`, configuration/inventory contracts, all four translation audits, and only the
  explicitly selected affected integration/DOM modules. It does not silently add the full suite.
- `release` has one 16-step plan: 13 active local steps, 2 required CI evidence steps (application
  and container smoke), and 1 honestly pending browser-smoke step owned by P5.4.

The non-dry release command fails before expensive work while a required step remains `pending`.
After P5.4 supplies the browser harness, the local release command can run active checks while the
same candidate commit must separately have both CI smoke jobs green.

## Optional and Experimental Isolation

`python tools/quality_gate.py --list-suites` reports three non-release surfaces:

- `storage-live` — optional automated PostgreSQL/MongoDB checks, owned by P5.1;
- `provider-live` — optional manual real-provider checks, owned by P2.1/P2.2;
- `experimental-ha` — Redis coordination/topology evidence, owned by the post-R1 backlog.

None is present in the production release plan or required CI. Their unavailable environment,
skip, or failure is reported under its own classification and cannot change the Core verdict.

## CI and Documentation

- Python 3.12 CI calls the same `fast` runner used locally; Python 3.14 retains its compile,
  partition, and complete Core checks.
- Production-blocking matrix, dependency, route, application-smoke, and container-smoke names use
  the `Required:` prefix. No optional or experimental suite is scheduled as a required job.
- README and CONTRIBUTING now direct task work to a real focused-module example rather than the
  complete suite.
- The release checklist points to the single release command and same-commit CI smoke evidence.

## Verification

### TDD evidence

The first test failed because `tools.quality_gate` did not exist. After implementing the runner,
contract tests exposed the expected stale CI/documentation and CI-status display. Once corrected,
7 tests passed. A real phase dry-run then exposed a direct-script import-path defect; a regression
test reproduced it before the bootstrap fix. The completed contract now reports:

```text
Ran 8 tests in 0.991s
OK
```

The final P0.3-P0.5 cross-regression slice also passed all 29 tests in 8.675 seconds.

### Required P0.5 execution

The exact fast command completed successfully:

```text
python tools/quality_gate.py fast
Backend test partition valid: core=167, experimental-ha=13.
Quality gate passed.
```

Its first run found one committed Ruff-format drift in `backend/core/coordination.py`; the canonical
formatter made the single presentation-only correction. Git Bash could not create its signal pipe
inside the Windows sandbox, so the unchanged gate was rerun outside that sandbox and passed. This
was an execution-environment restriction, not a skipped shell check.

The required non-executing audits also passed:

```text
python tools/quality_gate.py release --dry-run
release gate (16 steps)

python tools/quality_gate.py --list-suites
storage-live [optional]
provider-live [optional; manual]
experimental-ha [experimental]
```

No full Core suite, container build, provider call, or HA topology matrix was run for this task, in
accordance with the fixed verification cadence.

## Review

- Correctness: plans are deterministic, focused modules must exist in the Core manifest, and a
  pending required release check fails closed before expensive execution.
- Readability: one small declarative step model owns local commands and display; documentation uses
  the same four gate names.
- Architecture: the runner orchestrates existing Ruff, unittest, Node, yamllint, pip-audit, Git, and
  CI checks without entering application runtime or adding a dependency.
- Security: command arguments are fixed or validated against the discovered Core module allowlist;
  no shell interpolation, secret input, or external provider call is introduced.
- Performance: `fast` completed in seconds and omits the 167-module Core suite; task and phase scope
  remains explicit instead of growing automatically.
- Scope: P5.4 browser implementation, P1/P5 container evolution, live providers, optional storage,
  and experimental HA remain with their pre-existing owners.

Verdict: approved as the fixed P0.5 verification cadence.
