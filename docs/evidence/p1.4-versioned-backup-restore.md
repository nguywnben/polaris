## Result

The supported standalone SQLite runtime now exposes authenticated APIs for a passphrase-encrypted
portable backup, complete dry-run validation, explicit conflict handling, atomic restore with an
encrypted pre-restore snapshot, and a separate non-restorable sanitized inventory. The archive
contains exactly a versioned manifest and a consistent SQLite snapshot. It protects configuration,
credentials, routing, virtual keys, identity, quality policy, audit, bounded traces, migrations,
and durable usage state while excluding raw log files and prior recovery artifacts.

The encrypted envelope has one fail-closed suite: scrypt with fixed bounded parameters and
AES-256-GCM with authenticated metadata. ZIP members are never extracted and the parser enforces
exact member names, hashes, sizes, duplicate rejection, and SQLite integrity/schema checks. Upload,
decrypted archive, database, and SQLite validation time are bounded. PostgreSQL and MongoDB return
an explicit unsupported-backend response in R1.

Restore validates everything before mutation, defaults to `abort_if_configured`, and requires
explicit `replace` for a configured destination. It persists an encrypted snapshot before SQLite's
transactional backup replacement, rebinds every state-derived service/cache, and completes or
rolls back the critical section before request cancellation can escape. The SQLite cache reload
now replaces its prior snapshot rather than retaining keys deleted by restore.

The sanitized path reads only declared safe configuration and inventory keys, emits aggregate
credential/routing/key/identity/record counts, and excludes credential payloads, API and virtual
keys, password hashes, key previews, and restorable key material.

## Review Findings Resolved Locally

| Finding | Resolution |
| --- | --- |
| Auxiliary pricing file weakened atomic restore | Removed it; one SQLite artifact is the complete recovery authority. |
| Experimental HA checkpoint table was incorrectly required | Removed from the core requirement; retained only as a known inert compatibility table. |
| Runtime cache retained keys absent after restore | Cache reload now replaces the full snapshot; container proof verifies routing/key recovery. |
| Client cancellation could outlive threaded replacement | Critical replacement/reload is shielded and completes before cancellation returns. |
| SQLite connections relied on transaction-only context managers | All P1.4 direct connections now use deterministic closing. |
| 120 MiB database limit could exceed the 64 MiB envelope | Contract aligned to 45 MiB SQLite / 46 MiB expanded archive / 64 MiB upload. |
| Compression-ratio rejection could block sparse valid SQLite files | Removed the heuristic; strict absolute expanded/member bounds remain. |
| Unknown SQLite tables could enter restored state | Unknown tables fail closed; only core and one known inert compatibility table are accepted. |
| Non-table SQLite schema objects could bypass the table allowlist | Non-internal VIEW and TRIGGER objects now fail closed, with regression coverage. |
| Pre-restore responses could survive runtime reload | Restore invalidates the response-cache coordinator and its local/coordination state. |
| Recovery snapshots could accumulate without operator action | The runbook requires free-space checks and manual pruning while retaining an external known-good rollback point. |
| Passphrase length wording did not mention normalization | The contract now states that the 12–256 character boundary applies after NFKC normalization. |
