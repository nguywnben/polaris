# P4.4 — Access Lifecycle Completion

Date: 2026-09-10
Plan: `PROD-SELFHOST-R1`
Status: complete

## Result

The `/access` console now presents the deployment root key as an owner-recovery credential and
directs normal clients and automation toward restricted virtual keys. Six static SDK summary cards
were replaced by one copy-ready quickstart that follows the selected OpenAI, Anthropic, or Google
GenAI protocol and always uses the visible `YOUR_POLARIS_VIRTUAL_KEY` placeholder. It never reads the
root-key input, a console session, or a stored provider credential.

The existing virtual-key workflow remains complete: create, one-time reveal, use guidance, edit,
rotate, revoke, usage inspection, search, and status filtering. Cards expose last use, expiry,
requests/tokens per minute, daily/monthly budgets, scopes, model patterns, and unknown-price policy.
Fallback pricing now includes its configured USD-per-million value, and a zero-dollar hard budget
is displayed as a limit instead of being mislabeled as unlimited.

## Safety and Compatibility

- Create and rotate responses are the only API responses that contain a plaintext virtual-key
  secret. List, usage, edit, and revoke records remain hash/preview-only.
- Closing the one-time secret dialog synchronously clears its input and in-memory variable. The
  detached modal is emptied after unmount, and `pagehide` clears the value during navigation or
  reload. No browser storage is used.
- The console sends an optimistic `expected_revision` for edit, rotate, and revoke; the existing
  edit endpoint keeps it optional for pre-R1 client compatibility, while the new rotate and revoke
  endpoints require it. Stale updates return HTTP 409, refresh the list, and do not overwrite the
  winner.
- Rotate and revoke remain explicit confirmation actions. Revocation is terminal and leaves only
  the audit-safe key identity and preview.
- New clients should submit the revision returned by list/create. The console already does so, and
  no inference protocol changed.
