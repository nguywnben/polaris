# P3.6 — Models and Routing Workflow

Date: 2026-09-10
Plan: `PROD-SELFHOST-R1`
Status: implementation complete; candidate checks passed. See the working-tree caveat below.

## Result

Models now supports the lifecycle of the existing public `polaris` route: select discovered models,
validate the draft, create, edit the fallback order, save, prepare a Playground handoff, and delete
with confirmation. Users do not need to copy provider model IDs. Saved fallbacks that disappear
from discovery remain visible as temporarily unavailable; a healthy remaining fallback can still
be saved. Previously unknown IDs, an empty route, and a route with no available member fail
validation with stable, localized explanations.

The page exposes all five existing credential strategies and a provider selector derived from
discovery. Copy distinguishes global credential selection from ordered model fallback and explains
stored credential weights. Environment-owned settings are visibly locked. A route conflict does
not write the global strategy. If the route saves but the separate existing configuration API
fails, the console reports that partial result and retains the new route revision for retry.
Both model changes and strategy changes block handoff until saved. Stale validation responses are
discarded. Keyboard focus survives catalog selection and model reordering.

Validation describes discovery/blacklist availability, not a successful inference or a live
upstream probe. Request-time cooldown, capacity, retries, and health selection remain with the
existing P2.5 router. The public alias remains `polaris`; no arbitrary alias service, per-model weight
system, database migration, dependency, background worker, or new polling loop was introduced.

## API and Compatibility

- `GET /api/model-catalog` adds `model-routing.v1`, route revision/configured state, safe validation,
  and the effective global credential policy with environment locks.
- `POST /api/model-routes/polaris/validate` is side-effect-free.
- `POST /api/model-routes/polaris` creates a route, returning 201; an existing route returns 409.
- `PATCH` and `DELETE /api/model-routes/polaris` require `If-Match`; missing preconditions return 428,
  stale revisions return 409, and invalid drafts return 422.
- The original `PUT /api/model-pools/polaris` remains an unconditional compatibility upsert. It shares
  the single-worker write lock with the new lifecycle endpoints.
- All four new operations are classified in authorization, audit/exclusion, and product inventory.

The Phase 3 gate found a committed P3.3 compatibility regression: `/api/usage/stats` had changed its
schema and silently truncated the legacy response. This task restores the original endpoint and
moves the bounded Dashboard read to additive `/api/usage/stats/page`. Regression tests prove the
legacy response remains complete and the Dashboard response remains bounded. The immutable R1
compatibility fixture was not changed.

The seven untranslated pagination literals left by P3.4 were connected to the existing locale
keys during the Phase 3 exit review. No new localization task was added.

## Playground Boundary

P3.6 implements only the handoff specified in the fixed plan. The payload is exactly
`{schema_version: "playground-handoff.v1", source: "models", model: "polaris"}` and contains no key,
credential, prompt, or response. A bounded session item and `polaris:playground-handoff` event provide
the handoff; navigation activates when the Playground destination exists. Until P4.2/P4.3, the
console explicitly says that Playground is unavailable and no inference request was sent. This
evidence does not claim a completed Playground or an inference success.

## Working-tree Caveat

The raw Phase 3 gate initially reported four missing inventory entries and two compatibility
assertion failures. The inventory and P3.3 usage regression were corrected. A remaining raw
working-tree mismatch is caused by the pre-existing, unstaged addition
`model_config = ConfigDict(extra="forbid")` in `backend/core/models.py`: it changes the original
model-pool request schema. That user-owned edit was neither modified nor staged.

To verify the P3.6 candidate separately, the committed `HEAD:backend/core/models.py` was loaded
into memory before importing the application; all other modules were the current P3.6 files.
The **14 compatibility/inventory tests passed** against that candidate. The real file and immutable
baseline remained untouched. Therefore the candidate passes compatibility, but the current dirty
workspace must not be described as an unconditionally green full Phase 3 gate. Reconcile this
separate schema edit before including it in a release candidate. The two pre-existing deleted
historical report files also remain unstaged.
