# P1.1 Evidence — Authoritative Typed Configuration Schema

## Result

P1.1 is complete. Polaris now has one typed field contract for its 124 documented environment
variables. It classifies each field as Basic, Advanced, or Experimental and records its runtime
type, default, Settings owner, secret status, environment ownership, and live/restart/read-only
application mode.

The authoritative implementation is `backend/core/configuration_schema.py`. The committed
`docs/reference/configuration.md` reference is generated from it and is guarded by both a focused
test and `tools/configuration_reference.py --check`.

## Runtime and Settings Behavior

- Startup validates the environment before storage is opened. Invalid booleans, numbers, integer
  ranges, and enumerations fail with the exact variable name and accepted constraint.
- Unknown process variables remain ignored. Unknown names beginning with `POLARIS_` produce a warning
  so misspelled product controls cannot silently appear active.
- Stored settings are normalized and checked after migration and on reload.
- The Settings API returns schema metadata without configuration values or secret defaults.
- Environment locks, restart-required keys, system-write ownership, provider ownership, quality
  ownership, and resettable system fields derive from the schema.
- The previous route-local whitelist and more than 200 lines of duplicated scalar validation were
  removed. Provider-, quality-, and access-owned settings cannot be written through the generic
  system Settings endpoint.

Specialized OIDC, experimental coordination, and telemetry policy modules continue to enforce
their multi-field and transport security rules. The shared schema owns scalar boundaries and does
not weaken those fail-closed checks.

## TDD and Verification

The first focused test run failed because `core.configuration_schema` did not exist. Subsequent
boundary tests covered invalid integer syntax/ranges, invalid booleans and choices, unknown Polaris
controls, secret-safe Settings metadata, system update normalization, generated-reference drift,
and exact `.env.example`/Compose coverage.

The final focused task gate covered:

- `backend.tests.test_configuration_schema`
- `backend.tests.test_config_initialization`
- `backend.tests.test_config_security`
- `backend.tests.test_runtime_configuration`
- `backend.tests.test_product_surface_inventory`

The task gate passed all lint, format, bytecode, suite-partition, recursive JavaScript, strict YAML,
shell syntax, whitespace, and 38 focused tests. The partition now contains 169 Core modules and 13
experimental-HA modules.

The full Core suite and Phase 1 container/browser gate were intentionally not run: the frozen
cadence reserves those for their stated phase/release checkpoints. No Redis, multi-replica, or
provider-live suite ran.

## Review

- Correctness: documented environment names, Compose defaults, runtime startup, stored values, and
  Settings writes share executable field constraints.
- Security: reusable secret defaults are omitted from public metadata and generated reference;
  field validation occurs before storage or external initialization.
- Maintainability: configuration ownership replaces parallel hand-maintained allow/deny/reset
  lists and the generic route's validation block.
- Compatibility: public routes and response fields remain; Settings metadata is additive, and
  existing getter fallback behavior remains available for isolated compatibility callers while
  real startup is strict.
- Scope: no P1.2 Compose simplification, P1.3 setup flow, or experimental HA activation was pulled
  into this task.

Verdict: approved. Progress is 7/36; Phase 1 is 1/6. The next fixed task is P1.2.
