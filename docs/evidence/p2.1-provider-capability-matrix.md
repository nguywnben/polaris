# P2.1 — Provider Capability Matrix

Date: 2026-09-09
Plan: `PROD-SELFHOST-R1`
Status: complete

## Result

All nine provider/authentication variants advertised by the production console now derive from one
server registry. The versioned `GET /api/providers/capabilities` contract covers add, verify, test,
OAuth refresh, quota, model discovery, five normalized inference protocol families, disable,
export, and delete. `GET /api/providers` remains an exact v1 compatibility projection.

The credential UI stores the returned variant records and uses their operation sets for individual
card actions and mixed-selection eligibility. Provider-name checks no longer decide quota,
model-list, enable/disable, export, credit-mode, verify, test, or delete availability. A missing
catalog or unknown variant fails closed for provider-pool actions while read-only diagnostic views
remain available.

## Matrix disposition

- OAuth variants Google Antigravity, Grok Build, Codex, and Claude Code declare automatic token
  refresh; API-key variants and Ollama do not.
- Quota is advertised only for Google Antigravity, Grok Build, and Codex, matching implemented
  account quota/billing adapters.
- Every advertised variant supports add, verify, bounded test, model discovery, disable/re-enable,
  export, and delete.
- Every variant is eligible for the current OpenAI Chat Completions, OpenAI Responses, Anthropic
  Messages, Gemini-native, and Vertex-compatible ingress families. Detailed field translation
  parity remains P2.3 work and was not claimed here.
- The legacy `toggle` alias and the existing compatibility vocabulary remain available to 1.x
  clients without weakening the canonical `disable` capability.

The maintained public matrix and operation semantics are in `docs/provider-capabilities.md`.

## Failure contract

Unsupported single-credential operations return HTTP 422 with the stable
`credential_operation_unsupported` envelope, requested operation, and exact variant ID. Unknown
variants report `unknown`. Model discovery now applies this check before catalog access; existing
verification, tests, quota, export, mutation, and batch planning use the same registry. Tests prove
that rejected requests do not reach provider network calls or storage mutation and that error bodies
do not contain credential material.

## Compatibility

The first v2 implementation additively expanded the existing provider response model. The immutable
R1 compatibility guard correctly rejected that semantic change. The final design moved v2 to the
additive `/api/providers/capabilities` subresource and restored both the schema and runtime body of
`/api/providers`. The `r1-v1` fixture was not edited; its compatibility tests pass unchanged.

## Verification

The P2.1 task gate used the fixed task cadence. Lint, formatting across 417 files, Python
compilation, the `core=177`/`experimental-ha=13` partition audit, recursive JavaScript syntax,
strict YAML, and whitespace checks passed. Git Bash initially failed inside the Windows sandbox
with `Win32 error 5` while creating its signal pipe; only the six shell syntax checks were rerun
outside that sandbox and all passed.

The remaining focused gate passed 85 tests across:

- provider capability and authenticated catalog contracts;
- single-item unsupported-operation enforcement;
- credential card and batch-toolbar capability consumption;
- credential batch planning/execution and provider-pool filters;
- immutable R1 compatibility; and
- product-surface inventory ownership.

A final wire-compatibility review then found that filtering the v2 list changed only the ordering of
legacy `operations`. The projection now uses the explicit v1 order, and an additional 25 focused
catalog, matrix, and compatibility tests passed with an exact payload-order assertion.

No real provider credential, external provider call, complete Core suite, browser suite, or HA
topology matrix was run. Live provider smoke remains optional/manual, and the affected browser and
protocol integration gate remains scheduled once at the end of Phase 2.

## Scope review

- No provider, auth flow, public inference route, persistence layer, dependency, page, or plan task
  was added or removed.
- P2.2 error classification and bounded cancellation behavior were not implemented early.
- P2.3 protocol field-parity claims were not inferred from routing eligibility.
- Existing user-owned deletions under the historical W4.15 review directory were left untouched.
