# W4.13 adversarial review reconciliation

## Review boundary

This review covers the unactivated W4.13 durable-ledger inventory, migration domain, bounded
runner, and SQLite/PostgreSQL/MongoDB checkpoint repositories. A fresh-context internal reviewer
challenged the design after the first implementation. No W4.13 source was sent to an external
model. W4.13 still exposes no management endpoint, operator command, background migration, or
runtime backend switch.

## Findings and disposition

| Severity | Finding | Disposition |
| --- | --- | --- |
| Critical | A caller-supplied inventory could omit a not-ready family and change readiness after restart. | Fixed. The runner accepts only the closed `DURABLE_INVENTORY`; checkpoints bind the canonical manifest version and semantic checksum, and strict reconstruction rejects drift. |
| Critical | Source writes could make verification stale before activation. | Fixed at the contract boundary. Planning requires source mutation-barrier evidence, which is checked before/after copy, before/after verification, and before future activation. Production barrier acquisition remains gated to W4.18. |
| Critical | Backend labels did not prove that restart used the same physical endpoints. | Fixed. Source and target publish validated backend/instance descriptors; instance IDs are persisted and revalidated on every resume. Distinct instances of the same backend category are supported. |
| Critical | A boolean rollback-complete argument could forge reconciliation. | Fixed. The authority-flip shortcut was removed. W4.13 defines rollback invariants only; W4.18 must require evidence-bearing reverse copy, reconciliation, drain, and barrier verification. |
| High | Copying the migration-checkpoint family would recursively change the inventory during migration. | Fixed. It remains inventoried as control-plane metadata but is explicitly excluded from copied data families. |
| High | Generic target upsert semantics allowed silent overwrite. | Fixed. The contract now requires `put_if_absent_or_equal`; same-key/different-content writes fail as corruption. |
| High | Empty scans could verify without evidence that emptiness was intended. | Fixed. Planning persists a closed explicit-empty declaration per family; verification requires exact agreement between that declaration and the observed source count. |
| High | Source mutation could create a checksum mismatch that a copy cursor could not repair. | Fixed by the mutation barrier. A lost/invalid barrier prevents verification evidence from being published; W4.13 does not attempt unsafe live recopy. |
| High | Checkpoint creation accepted a non-initial revision. | Fixed. All repositories require revision 1 at creation and exact +1 compare-and-set updates. |
| Medium | Verification accumulated full record sets and was not restart-safe. | Fixed for memory safety. Digests stream in stable key order with duplicate/order checks. A restart deliberately rescans the current family from offset zero; only bounded metadata is persisted. |
| Medium | Repository-provided opaque cursors could place secrets in checkpoints. | Fixed. Copy state is a non-negative numeric offset equal to the accepted record count; no repository cursor is persisted. |

## Accepted boundaries and follow-up

- PostgreSQL and MongoDB checkpoint behavior is covered at the driver boundary with deterministic
  fakes; W4.13 makes no live-service parity claim. W4.14 owns live backend adapter parity.
- The current checkpoint repositories store the latest strict revision rather than an append-only
  revision history. They reject invalid creation, stale/non-monotonic updates, and record/column
  mismatch, but cannot prove historical revisions that predate the retained row. Operational
  audit evidence for migration commands belongs to W4.18.
- Stable non-secret instance fingerprint generation, production record adapters, mutation-barrier
  acquisition, reverse reconciliation, and operator approval are intentionally not implemented in
  W4.13. Their absence keeps `ready_to_switch` and runtime authority activation closed.
- The canonical manifest checksum excludes explanatory prose; changing behavior-bearing manifest
  fields changes the checksum, while editorial wording does not invalidate resumability evidence.

## Verification expectations

Closure requires focused abuse/transition/repository tests plus the repository-wide lint, format,
compile, dependency, frontend syntax, secret, and regression gates. Runtime remains standalone with
one worker and one replica after restart.
