# W4.14 adversarial review reconciliation

## Review boundary

This review covers the W4.14 selected-backend usage/cost repositories, durable hard-budget
reservation journal, legacy SQLite import, reporting compatibility facade, readiness integration,
and runtime admission/settlement path. A fresh-context internal reviewer performed repeated
read-only passes after each correction. No W4.14 source was sent to an external model.

## Findings and disposition

| Severity | Finding | Disposition |
| --- | --- | --- |
| Critical | A successful provider response with uncertain durable settlement could be released during final cleanup and become zero spend after restart. | Fixed. Uncertain settlements retain their durable estimate; expiry remains a conservative enforcement-only charge for the applicable budget window. |
| Critical | PostgreSQL initialization validated schema before executing all index DDL. | Fixed. Validation runs only after all five additive DDL statements; the test asserts the execution order. |
| High | The local 100,000-reservation ceiling was checked before an `await` and claimed afterward, so concurrent admission could exceed it. | Fixed. A lock-protected claim is made before the first ledger await, rolled back on reserve failure/rejection, and covered by a concurrent capacity test. |
| High | Compatibility reporting could materialize an unbounded number of rows. | Fixed. All three repositories query a 100,001-row sentinel and fail closed above the 100,000-row ceiling. |
| High | Readiness reflected service initialization rather than proving that the selected ledger relation or collection was available. | Fixed. Each probe performs a bounded read against the actual SQLite/PostgreSQL ledger relation or verifies the MongoDB collection exists. |
| High | Local durable and pending-settlement tracking could grow without pruning or a hard bound. | Fixed. Tracking is TTL-pruned, lock-protected, and hard-capped; new hard-budget admission returns 503 at capacity. |
| High | Existing backend objects were checked mainly by name, allowing incompatible schema to be accepted. | Fixed for SQLite and PostgreSQL with exact column type/nullability, primary/unique/check constraints, required indexes, and migration-schema validation. MongoDB initialization continues to require transaction capability and exact materialized-record decoding. |
| High | Legacy import could publish a marker or partial target state after source mutation. | Fixed. Import, target verification, and append-only marker update are one transaction; source shrink or immutable-prefix mutation fails closed and rolls back. |
| Medium | Reservation revisions and public SQLite timestamps accepted Python values that were numerically coercible but not contract-exact. | Fixed. Boolean/float revisions and non-finite or wrong-type timestamps are rejected by strict domain validation. |
| Medium | Settlement failures could log exception content containing identifying or backend details. | Fixed. Logs retain only a bounded exception type and stable event wording. |

## Accepted boundaries and follow-up

- Live PostgreSQL and MongoDB parity suites are present but remain opt-in because no live test URI
  is configured in this workspace. Driver-boundary transaction, schema, idempotency, conflict,
  reporting, and capability tests pass deterministically; no live-service claim is made.
- The canonical migration inventory keeps `USAGE_LEDGER` and `HARD_BUDGET_RESERVATION`
  `switch_ready=false`. Production migration record adapters, stable endpoint fingerprints,
  operator tooling, and live backend evidence are still required before authority can reach
  `ready_to_switch`; W4.18 owns that activation boundary.
- RPM and TPM remain on the in-process state-store implementation. Redis semantic parity belongs
  to W4.15, and multiple workers/replicas remain rejected.
- Conservative unresolved estimates are intentionally excluded from measured usage reports. They
  protect hard-budget admission from silent zero spend but may temporarily reduce available budget
  until the daily/monthly window expires.

## Verification evidence

- Repository-wide Ruff lint and format, compileall, dependency consistency, diff checks, frontend
  JavaScript syntax, YAML syntax, shell syntax, and the dependency vulnerability audit pass.
- The final internal review found no remaining closure blocker after the PostgreSQL ordering and

- Runtime remains standalone, source-authoritative, one worker, and one replica. W4.14 changes no
